@slide title Les tests dans le pipeline
Principe en schémas · Domaine 1
Quel test à quelle étape, les builds sur pull request, et le code de sortie qui décide
@end
L: Les tests dans un pipeline. Rémy, qu'est-ce que l'examen attend ?
R: Trois choses. Savoir quel type de test placer à quelle étape. Savoir lancer les tests automatiquement sur une {pull request}. Et comprendre que c'est le code de sortie d'une commande qui fait réussir ou échouer une étape.

L: Voici le chemin d'un changement, de la {pull request} à la production.
R: La règle : les tests rapides et nombreux le plus tôt possible, les tests lents et coûteux plus tard, sur un environnement proche de la production.
@show tpr v1
@focus src v1 tpr
R: Sur la {pull request} : un build rapide, l'analyse du code et les tests unitaires. Le développeur a son retour en quelques minutes, avant le {merge}.
@show tunit v2
@focus build v2 tunit
R: À l'étape de build : tous les tests unitaires, avec la couverture de code, et l'analyse de sécurité du code. {CodeBuild} publie les résultats dans ses {reports}.
@show tint v3
@focus tst v3 tint
R: Une fois l'application déployée dans un environnement de test : les tests d'intégration et d'acceptance, qui appellent les vraies {API} et les vrais services.
@show tload v4
@focus stg v4 tload
R: En {staging} : les tests de charge et de performance, et les tests d'interface. Pour la charge à grande échelle, {AWS} propose la solution {Distributed Load Testing on AWS}, qui lance les tests depuis des conteneurs {Fargate}.
@show tprod v5
@focus prd v5 tprod
R: Et en production : un déploiement {canary}, des {hooks} de validation, des {canaries} {Synthetics}, et des alarmes qui déclenchent le {rollback}. Avant la production, une approbation manuelle si la question l'exige.
@unfocus
L: Et pour appeler un service {AWS} pendant les tests ?
R: Une action {CodeBuild} de test, une action {invoke} {Lambda}, ou une action {Step Functions} pour orchestrer un scénario de test complet.

L: Comment lancer les tests automatiquement sur une {pull request} ?
R: Avec {CodeCommit}, la création ou la mise à jour d'une {pull request} émet un événement. Une règle {EventBridge} lance un build {CodeBuild} sur la branche source.
@show res a4
@focus cb a4 res
@flow a4
R: Le résultat est renvoyé sur la {pull request}, en commentaire, et peut compter comme un vote d'approbation exigé par une {approval rule}.
@show gh g1 g2
@focus pr g1 gh g2 cb
@flow g1 g2
R: Avec {GitHub} ou {Bitbucket}, c'est encore plus direct : un {webhook} {CodeBuild} filtré sur les événements de {pull request}.
@show rep a5
@focus cb a5 rep
R: Les {reports} {CodeBuild} affichent les tests au format {JUnit}, {NUnit} ou {Cucumber}, et la couverture de code au format {JaCoCo}, {Cobertura}, {Clover}, {SimpleCov} ou {LCOV}.

L: Et comment {CodeBuild} sait qu'un test a échoué ?
R: Par le code de sortie. Chaque commande du {buildspec} renvoie un code. Zéro : la phase réussit. Autre chose : la phase échoue.
@show next fail stop e2 e3 e4
@focus ko e3 fail e4 stop
@flow e3 e4
R: Une phase en échec fait échouer le build, donc l'action du pipeline, et rien n'avance vers la production. Le réglage {on-failure} d'une phase permet de choisir {ABORT} ou {CONTINUE}.
@show vs rb e5
@focus vs e5 rb
@flow e5
R: C'est le même principe dans {CodeDeploy} : un script de {hook}, par exemple {ValidateService}, qui sort avec un code différent de zéro fait échouer le déploiement, et déclenche le {rollback} s'il est activé.
